node: ai-agent in production

AI Sales Agent “Petr” — conversational commerce

Problem: an e-commerce store with 20,000 SKUs (laptop parts) — managers can’t cover every chat, and off-the-shelf chatbots can’t actually sell from a live catalog: check stock, pick compatible parts, quote price and delivery.

the actual production workflow — 46 nodes, live on the site & CRM

  • Multi-tool orchestration (LangChain agent): SQL + vector search, product compatibility, laptop-matrix finder, calculator, reasoning tool.
  • Hybrid RAG — Supabase pgvector + PostgreSQL: vectors alone fail on exact part numbers, SQL alone fails on fuzzy human questions.
  • Supplier fallback: out of stock → the agent searches supplier sites, calculates delivery & final price, and signals procurement what to buy.
  • Cost-aware model routing (gpt-5 → gpt-5-mini → gpt-4.1) + Redis message-debounce. Token cost is a production constraint — I treat it like one.
  • Human-in-the-loop: hands off to a live manager at the right moment; Telegram alerts to manager & procurement.

knowledge-ingestion pipeline: Drive → PDF → embeddings → vector store

node: integration in production

Bitrix24 ↔ 1C ↔ Website — deep CRM↔ERP integration

Problem: managers juggled the CRM, the ERP (1C — the accounting system of record) and the website. Multi-warehouse + multi-organization accounting made every sale a multi-document ritual.

  • Custom deal widget inside the CRM: product selection, splitting a deal into sub-deals by warehouse/organization, stock reservation — multi-step ERP operations in a couple of clicks. 33 shipped iterations.
  • Full payment domain: cash & card acquiring (idempotent by RRN), bank-statement parsing with an auto-classifier posting into the ERP, online payments via HMAC-signed webhooks with a manager claim-flow.
  • Custom HTTP service inside the ERP (1C/BSL extension, TLS-pinned) + PHP proxy layer + REST/webhook clients — the integration backbone.
  • AI-assisted module pipeline: AI generates ERP extension modules (BSL); delivery automated — git-diff guard → packaging → SFTP → build watcher → check/apply/rollback — while production apply stays a separate authorized step.
  • Ops maturity: own secrets-management layer, zero-downtime credential-rotation runbook, OAuth keepalive automation.

node: document-ai in production

Document-AI service — receipt & waybill recognition

Problem: accounting paperwork arrives as photos and PDFs — receipts, waybills — and someone retypes them into spreadsheets by hand. Slow, error-prone, and a shared bot for several companies needs isolation and cost control, not just OCR.

the actual production workflow — Telegram intake to structured client tables

  • Recognition pipeline: Google Vision OCR (images & PDF) → LLM field extraction (OpenAI) → structured rows in per-client Google Sheets tables, created and initialized automatically.
  • Multi-company by design: user & company lookup, whitelist, access control — one bot serves several organizations with isolated client tables.
  • Cost governance: per-user monthly limits with usage counters — AI spend per user is bounded, not open-ended.
  • Document-type routing (receipt vs waybill) with separate extraction schemas, plus file validation: type, size caps, invalid-file handling.
